# Архитектура

## Подход

Проект начинается как модульный монолит. Это сохраняет простое развёртывание и
транзакции, но разделяет предметные области так, чтобы фоновые задачи или Telegram
Mini App можно было развивать независимо.

Микросервисы на старте не используются: они увеличат эксплуатационную сложность,
не дав ценности при текущем масштабе.

## Планируемый стек

- Python 3.13;
- FastAPI для HTTP API и служебных endpoints;
- aiogram 3 для Telegram-бота;
- PostgreSQL как основной источник данных;
- SQLAlchemy 2 и Alembic;
- Redis для короткоживущих блокировок и очереди;
- отдельный worker для фоновой доставки уведомлений;
- pytest, Ruff и mypy для проверки кода;
- Docker Compose для локальной разработки.

Конкретный инструмент фоновых задач выбирается при создании каркаса после
небольшого технического прототипа. Доменный код не должен зависеть от него.

## Модули

```text
src/
  medication_reminder/
    users/
    medications/
    schedules/
    intake_events/
    medication_sets/
    reminders/
    telegram/
    shared/
```

- `users` — Telegram-пользователь, настройки и часовой пояс;
- `medications` — справочные данные препарата и назначения пользователя;
- `schedules` — правила повторения и генерация будущих событий;
- `intake_events` — конкретные запланированные действия и их история;
- `medication_sets` — утренние и вечерние группы;
- `reminders` — планирование и доставка уведомлений;
- `telegram` — команды, диалоги, кнопки и преобразование ответов в команды системы;
- `shared` — конфигурация и небольшие общие технические компоненты.

`shared` не должен становиться местом для несвязанных вспомогательных функций.

## Слои модуля

Внутри сложного модуля допускаются:

```text
domain/          чистые сущности и правила
application/     пользовательские сценарии
infrastructure/  PostgreSQL, Redis, Telegram и очередь
presentation/    обработчики входящих запросов
```

Слои создаются только там, где они реально нужны. Простые модули не обязаны иметь
пустые каталоги ради симметрии.

## Основные сущности

- `User` — Telegram ID, часовой пояс, язык и настройки;
- `Regimen` — пользовательское назначение: название и форма препарата, точная доза,
  период действия и текущее состояние;
- `ScheduleRule` — версия правила повторения;
- `IntakeEvent` — конкретное действие на конкретную дату;
- `IntakeEventHistory` — переходы состояния и источник действия;
- `MedicationSet` — именованная группа назначений;
- `ReminderAttempt` — попытка доставки уведомления.

## Важные границы

- Telegram-обработчик не содержит расчёта расписаний;
- ORM-модели не передаются напрямую в Telegram-интерфейс;
- планировщик не меняет медицинские данные назначения;
- генератор расписания является детерминированной чистой логикой;
- отправка уведомления отделена от фиксации результата доставки;
- все обработчики callback-кнопок идемпотентны;
- дата и время получаются через внедряемый clock, чтобы тесты не зависели от
  текущего времени.

## Транзакции и конкурентность

Подтверждение события выполняется в транзакции с проверкой текущего состояния.
Одновременное нажатие кнопки и обработка фонового напоминания не должны создавать
два результата или возвращать событие в предыдущее состояние.

Worker выбирает готовые уведомления небольшими порциями и блокирует их так, чтобы
одну запись не обрабатывали два процесса. Уникальный ключ попытки доставки служит
дополнительной защитой.

## Стратегия тестирования

- модульные тесты генератора расписаний и переходов состояний;
- тесты прикладных сценариев с заменяемыми репозиториями и clock;
- интеграционные тесты PostgreSQL для транзакций и ограничений;
- небольшое число сквозных тестов Telegram callback-сценариев;
- отдельные тесты на смену часового пояса и граничные даты.

## Последовательность реализации

1. Каркас приложения, конфигурация и проверки качества.
2. Пользователь и первичная настройка часового пояса.
3. Назначения.
4. Чистый генератор расписаний.
5. Запланированные события и переходы состояний.
6. Telegram-диалоги создания и редактирования.
7. Worker и надёжная доставка уведомлений.
8. Наборы и групповые подтверждения.
9. История и подготовка API для Mini App.
